### 架构摘要

保留现有 coding-agent 作为可嵌入的产品内核，在其外部增加传输无关的应用服务层和薄协议适配层。独立服务进程统一持有 Session、Run、待审批事项及可恢复的客户端视图，三类客户端复用相同的业务契约。

首期建议使用 HTTP + JSON 承载命令与查询，使用 SSE 承载事件；通过“一致性快照 + 有序增量”恢复界面，而不是把一个长期 HTTP 请求等同于一次 Agent 任务。

### 文档使用说明

本文件整理本次讨论的总体设计，不表示新增模块、接口或恢复能力已经实现。用户已确认多端接管目标，并选择统一 API 默认采用严格的产品 Run 级补充输入投递语义；取消请求允许最终正常完成。其余模块名称、路由、字段和实施分期仍为建议基线，需在详细设计中固化。正文中的代码和 JSON 仅用于说明协议语义，不是可直接调用的现有接口。

## 范围及非目标

**首期范围：**单用户、多客户端；同一服务托管多个会话；客户端退出后任务继续；运行结果查询；流式展示；工具审批；会话快照与断线重连；明确的取消、关闭和失败语义。

# 01 定位、现有基础与设计原则

## 1.1 产品定位与核心场景

将下一阶段定位为“可脱离客户端运行的 Jcode 应用服务”，而非为 Java 方法简单添加 HTTP 包装。TUI、WebUI、Desktop 是平等的客户端；会话和运行属于服务进程，不属于窗口、终端、HTTP 请求或 SSE 连接。

“接管”表示重新连接原服务并恢复视图，不表示保存后重新执行，也不表示把内存会话移交给另一个客户端。远程服务上的任务被本地 Desktop 接管后，仍在远程工作区执行。

## 1.2 可复用的现有基础

下表依据固定仓库基线的源码及既有测试描述现有能力。新的输入契约单独列为目标能力，不能由现有测试推导其已经实现。[R1–R9]

| 现有基础 | 应保持的边界 | 外层需要补齐的能力 |
|---|---|---|
| ai / ai-providers / agent-core / coding-agent 分层 | 不把网络框架或 UI 引入内核 | 应用用例、协议与服务启动入口 |
| CodingAgentSession 产品门面 | 继续管理运行、历史及编码产品逻辑 | 会话注册、标识、查找与生命周期托管 |
| 产品事件及异步 EventSink | 保留内核事件语义与失败传播 | 对外 DTO、事件排序、投影与重连 |
| JSONL 会话历史及文件所有权 | 正式历史仍由内核维护 | 统一 writer 所有者、客户端只经 API 访问 |
| 异步 CodingToolPolicy | 授权仍发生在工具执行管道内 | 跨客户端待审批事项与决策提交 |
| Session / Agent 对象持有的输入队列 | 明确区分现有跨 Run 保留行为与新的严格模式 | 内核增加输入身份、产品 Run 范围、应用确认及终结结算 |

## 1.3 五项设计原则

**统一行为而非只统一路由。**三个客户端不分别管理运行、审批、分支和恢复规则；正式客户端不绕过应用服务直接操作内核。

**命令、执行、观察分离。**请求返回接纳结果，Run 独立执行，事件和查询负责观察；观察中断不等于任务取消。

**快照与事件协同。**历史与实时状态共同组成可恢复视图；SSE 不是唯一事实来源，也不是永久日志。

**显式副作用与保守恢复。**取消不回滚已完成的文件修改；断线不自动重提任务；崩溃后不自动重放未知结果的工具操作。

**薄应用层、适度扩展。**复用现有 Agent Loop、历史树、压缩、模型与资源能力；首期不引入通用工作流引擎、消息中间件或分布式架构。

# 02 总体分层与模块依赖

## 2.1 分层结构

| 层次 | 模块 / 组件 | 主要职责 |
|---|---|---|
| 客户端 | TUI / WebUI / Desktop | 输入、展示、通知、连接管理；共用相同业务规则 |
| 客户端契约 | 协议类型及 SDK | 命令调用、鉴权、订阅、重连、去重和视图更新 |
| 传输与宿主 | jcode-server | HTTP / SSE、认证、校验、错误映射、服务发现与启动 |
| 应用服务 | jcode-app | 会话托管、操作接纳、Run 登记、投影、审批及订阅隔离 |
| 产品内核 | coding-agent | 现有编码会话、工具装配、历史树、压缩及资源能力 |
| 基础能力 | agent-core / ai / ai-providers | 通用运行时、模型协议及 Provider 实现 |

调用方向自上而下；事件由内核进入应用投影，再向客户端发布。框架异常、网络连接和 UI 对象不应反向进入产品内核。

## 2.2 建议模块布局

```text
Jcode/
  ai/                  # 保留
  ai-providers/        # 保留
  agent-core/          # 保留
  coding-agent/        # 保留
  jcode-protocol/      # 对外 DTO、错误与事件 schema
  jcode-app/           # 传输无关的应用服务
  jcode-server/        # 服务启动与 HTTP / SSE 适配
```

jcode-protocol 不依赖 coding-agent 或具体网络框架；jcode-app 依赖内核及协议模型；jcode-server 负责组合与暴露应用服务。若先合并 Maven 模块，也应在包与测试层保持同样的依赖边界。

## 2.3 分层约束

**应用层不重复内核。**不重新实现模型循环、工具执行、历史分支或摘要算法；只组织用例、登记身份、校验接纳条件和维护客户端视图。补充输入的投递资格及应用状态由内核权威管理，应用层保存其投影，不建立另一套并行可执行队列。

**协议层不泄露实现。**不直接序列化内部 AgentMessage、Throwable 或整棵 Java 事件对象；使用显式映射的稳定 DTO，不暴露 Java 类型名、凭证、Provider 私有 replay state 或无关上下文。现有产品事件仍嵌套运行时事件，因此需要这一适配边界。[R3][R5]

**宿主层不制造第二套规则。**鉴权和传输处理可以在 server，业务冲突与状态转换应集中到 app。Java 嵌入式能力继续保留，但不作为正式三端绕过统一应用服务的路径。

# 03 进程拓扑与服务生命周期

## 3.1 默认服务拓扑

建议一个用户配置目录对应一个 Jcode 服务实例，由该实例托管多个工作区与多个 Session。允许显式使用不同配置目录建立隔离实例，但不默认按窗口、项目或会话启动多个互不知情的服务。

客户端可以发现或启动服务，但不拥有服务生命周期。服务不得依赖原客户端的 stdin / stdout，或被客户端退出清理逻辑连带终止；具体后台化和系统服务方式由操作系统适配实现。

## 3.2 生命周期规则

| 动作 / 事件 | 设计行为 |
|---|---|
| 退出 TUI、关闭网页、退出 Desktop | 关闭该客户端订阅；不取消 Run，不关闭 Session |
| 最后一个客户端离线 | 服务继续；投影、历史和待审批事项继续维护 |
| 显式取消 Run | 校验 runId，记录 cancelRequested 并关闭新补充输入接纳；进入 cancelling，依据实际结果结算 |
| 关闭 Session | 首期默认要求空闲；释放资源并保留历史 |
| 删除历史 | 单独设计与授权；不与关闭或取消混同 |
| 显式停止服务 | 有活动工作时拒绝隐式退出；可选择排空等待，或显式取消后停止 |
| 服务停止过程 | 先停止接纳新任务，再等待 / 取消在途工作，最后释放 writer 和资源 |

订阅数为零不是会话卸载条件。首期不自动卸载运行、维护或待审批中的 Session；空闲回收策略留待后续设计。

## 3.3 服务发现与实例识别

客户端启动时：定位用户运行目录 → 读取实例描述 → 连接并完成认证、实例身份和协议版本握手 → 进入会话列表。无可用服务时，再在进程级互斥保护下启动并等待就绪。

实例描述建议包含 endpoint、instanceId、PID 与协议版本，不在可公开读取的描述文件中保存明文长期凭证。不能只根据 PID 或端口判断身份；陈旧描述需在身份校验后处理。

认证失败或版本不兼容应明确报告，不应悄悄启动第二个实例。多个客户端并发启动时，应通过用户级锁和就绪检查避免重复服务。

## 3.4 本地与远程

本地 TUI、WebUI、Desktop 均连接同一 loopback 服务；远程场景连接云主机服务，工作目录和命令执行位置仍属于云主机。关闭客户端与用户登出、机器休眠或主机关机是不同事件：后者能否继续运行取决于部署模式，不属于本期客户端接管承诺。

# 04 领域对象与托管会话

## 4.1 核心对象

| 对象 | 身份与职责 | 生命周期 / 约束 |
|---|---|---|
| ServiceInstance | instanceId；服务进程和能力边界 | 进程重启产生新的实例身份 |
| Workspace | workspaceId；服务端目录及访问配置 | 不等于浏览器本地目录；不自动提供隔离 |
| Session | sessionId；长期会话及当前历史分支 | 可跨客户端存在；关闭不删除历史 |
| Run | runId；一次 prompt / continue 产品运行 | 可包含多轮模型调用、工具及内部恢复 |
| InputCommand | commandId；一次用户输入及回执 | 区分 prompt、steer、follow-up，不隐式改写意图 |
| InputRecord | inputId；一条 steer / follow-up 的身份及应用结果 | 由 Session 保存和查询，首次注入严格绑定 targetRunId；记录不等于跨 Run 执行资格 |
| Approval | approvalId；具体工具调用的授权事项 | 绑定会话、运行、工具及不可变请求快照 |
| Subscription | subscriptionId；一次客户端观察连接 | 关闭只影响观察，不影响执行 |

## 4.2 ManagedSession 的内部组合

```text
ManagedSession
  CodingAgentSession       复用现有产品内核
  SessionProjection        可恢复客户端视图
  RunRegistry              接纳记录及运行结果
  ApprovalCoordinator      待审批事项和决策
  ReplayBuffer             有界近期事件
  Subscriptions            各客户端独立订阅
```

SessionRegistry 统一负责 ManagedSession 的查找、加载与释放。同一服务内，不因多个客户端访问而多次打开同一历史文件；历史 writer 由服务统一持有。

## 4.3 视图不是第二份业务内核

SessionProjection 组织当前 Run、历史位置、流式消息、工具进度、审批、输入记录及必要配置。输入记录依据内核的权威状态更新，Session 提供查询；记录保留期限与持久化边界见 §11。投影服务界面恢复，不替代 JSONL 正式历史，不重新决定输入是否应用、工具是否执行或历史如何分支。

历史较大时通过历史版本与分页游标读取，不要求 snapshot 每次携带完整会话。客户端草稿、滚动位置和面板布局首期各自保存。

## 4.4 标识与关联

事件使用 sessionId / runId / inputId / messageId / partId / toolCallId / approvalId 等标识关联对象。流式 messageId、已应用 inputId 与最终历史 entryId 的关系必须由可靠接缝建立，不按文本、时间戳或列表位置猜测。

### 4.4.1 现有行为

当前 PendingMessageQueue 保存 AgentMessage，提供入队和出队，没有独立输入身份、目标 Run 或应用确认。队列归属于长期存活的 Session / Agent 对象：完成阶段迟到接纳、取消或模型失败后仍在队列中的输入，可能被后续 Run 消费；branch() 与 resetLeaf() 也保留这些队列。现有测试明确保护了上述跨 Run 行为。[R2][R8][R9]

客户端及应用层不得因断线、回执丢失或应用状态不明而重复提交同一输入。这一重试约束不改变当前内核的跨 Run 队列行为，也不表示队列已支持跨进程持久化。

### 4.4.2 统一 API 的目标契约

统一 API 默认采用严格的产品 Run 级投递：输入记录由 Session 保存和查询，每条 steer / follow-up 的首次注入资格只属于 targetRunId。目标 Run 最终结束后，未应用输入保留为可查询的终结记录，不自动进入后续 Run。该保证依赖新增内核能力，替代此前“首期沿用现有投递语义”的建议。

steer 在目标 Run 允许的后续模型调用边界注入；follow-up 在目标 Run 原本准备结束时注入，使同一 Run 继续执行。二者只区别注入时机，follow-up 不创建下一 Run。未来如需跨 Run 任务积压，应提供显式能力。

绑定范围是一次产品 Run，包含多轮模型与工具交互，也包含上下文溢出后的压缩和内部 continueAfterFailure()。内部恢复维持原输入范围；产品终态之后由用户显式发起的 prompt / continue 才创建新的 Run。

已经进入正式历史的输入可以随历史被后续 Run 读取，这属于历史继承。严格绑定仅终结尚未应用输入的首次注入资格，不删除历史、不撤回模型已经看到的内容，也不回滚工作区修改。

# 05 状态模型与并发接纳

## 5.1 生命周期、活动与执行阶段分开表达

建议 Session 使用 lifecycle（open / closing / closed）和 activity（idle / running / maintaining）两个维度，避免把对象是否存在与当前是否忙碌混为一谈。Run 使用下列状态：

```text
accepted -> running -> completed | failed | cancelled
accepted / running -> cancelling -> completed | failed | cancelled
accepted -> failed
```

accepted 后也可能启动失败而直接进入 failed。cancelling 只表示取消请求已接纳，不预先决定最终结果，不代表进程树已清理，也不保证已有副作用被撤销。取消与正常完成竞争时，应依据实际执行结果及基础设施结算结果单次提交终态，不能因为取消请求先被记录就覆盖正常结果。

Run 单独记录 cancelRequested；例如执行已完成、仍在结果交付时接纳取消，最终可以是 completed 且 cancelRequested = true。已经提交的终态不被后到取消改写。CompletionStage 正常完成也不必然表示成功：CodingAgentRunResult 中的 StopReason.ERROR 应映射为 failed，ABORTED 应按取消结果处理，基础设施异常需独立归一化。

Run 另设 phase 描述模型调用、工具执行、摘要等阶段。待审批列表独立存在，不因一个工具待审批就断言整批并行工具都已停止。

## 5.2 接纳矩阵

以下均要求身份授权通过；“允许”仍需校验具体对象和内核语义。

| 操作 | 空闲会话 | 运行中 | 维护中 |
|---|---|---|---|
| prompt / continue | 可接纳一个 Run | 返回 SESSION_BUSY | 返回 SESSION_BUSY |
| steer / follow-up | 拒绝：无目标 Run | 仅目标 Run 输入接纳仍开放时允许；取消中或最终结束中返回 RUN_INPUT_CLOSED | 拒绝 |
| cancel Run | 返回该 Run 的已有状态 | 校验 runId 后请求取消 | 不误取消维护操作 |
| 修改模型 / 分支 / 压缩 / 重载 | 依内核规则接纳 | 冲突，不暗中排队 | 冲突 |
| 审批响应 | 校验事项状态 | 可独立处理 | 仅在事项确实有效时处理 |
| snapshot / 订阅 / 查询 | 允许 | 允许 | 允许 |
| 关闭 Session | 允许 | 首期要求先明确取消 / 等待 | 首期要求先完成维护 |

输入接纳是否开放是内核权威状态，与 isRunning() 分开判断。进入 cancelling 或确定产品 Run 最终结束时关闭接纳；即使完成事件仍在等待 sink、running 尚未释放，也不得再接纳新输入。内部压缩与恢复不是最终结束，不因此关闭目标范围。

取消关闭新输入接纳后，已接纳输入与正在进行的上下文提交按真实先后关系结算；不把已进入历史的输入改成 not_applied。Run 终态发布前，所有已接纳输入都应具有可查询的应用结果或明确的待核对状态，不能仍以 pending 表示可继续投递。

## 5.3 接纳与执行不能使用同一个长时间阻塞队列

每个 Session 只串行化短临界区：检查状态、预留占用、登记标识、提交变化。模型调用、工具执行、审批等待和网络写入不能持有该临界区；否则取消或审批会被排到任务结束之后。

协议级冲突判断应与真正内核接纳协调，不能先检查 isRunning() 再无保护地执行。应用服务维护占用状态，仍由内核保留最终合法性检查。对取消使用明确 runId，对分支与配置修改使用预期版本，避免迟到请求影响新的工作。

输入接纳、声明应用及目标范围关闭必须具有可判定的先后关系。接纳先发生时，建立稳定 inputId，随后确认应用或结算未应用；关闭先发生时拒绝新输入。出队只取得内部处理资格，不能抹去权威记录；取消发生在出队与正式历史提交之间时，仍须准确结算该输入。

维护操作建议使用 operationId 和独立结果查询，不把压缩、重载伪装为普通聊天 Run。其取消能力需单独映射，不复用“取消当前 Run”。

# 06 统一 API 与协议边界

## 6.1 协议建议

首期采用 HTTP + JSON 承载命令和查询，SSE 承载服务端事件。三端共用同一套请求、响应、错误和事件 schema。对外契约与传输实现分离，但不同时实现多套传输。

交互式 PTY 后续可增加独立 WebSocket 通道；JSON-RPC、进程内传输或其他适配不是当前必要前置。框架选择保持开放，不能仅为实现 SSE 而改写整个内核的异步模型。

## 6.2 首期接口草案

下表是语义目录，不是已发布 OpenAPI。路径均以 /v1 为前缀，表中 {s}、{r}、{a} 分别表示 sessionId、runId、approvalId。

| 方法 | 路径（省略 /v1） | 行为 |
|---|---|---|
| GET | /capabilities | 实例身份、协议版本、功能及限制 |
| POST / GET | /sessions | 创建 / 列出会话；创建时指定已授权工作区 |
| GET | /sessions/{s}/snapshot | 一致性运行视图及事件游标 |
| GET | /sessions/{s}/history | 指定历史版本 / 分支的分页历史 |
| POST | /sessions/{s}/runs | prompt 或 continue；返回接纳回执 |
| GET | /sessions/{s}/runs/{r} | 查询运行状态、结果与错误 |
| POST | /sessions/{s}/runs/{r}/inputs | 明确 mode 的 steer / follow-up |
| GET | /sessions/{s}/inputs/{inputId} | 查询补充输入的 targetRunId、状态及历史关联；不要求目标 Run 仍活跃 |
| POST | /sessions/{s}/runs/{r}/cancel | 取消指定 Run，不指向“任意当前任务” |
| GET | /sessions/{s}/events | 按游标重放并衔接实时 SSE |
| POST | /sessions/{s}/approvals/{a}/resolve | 提交一次审批决定 |
| POST | /sessions/{s}/close | 空闲关闭，不删除历史 |

## 6.3 API 行为约束

长任务返回接纳回执，不维持“直到模型完成”的请求依赖。客户端可以关闭响应连接，随后用 runId 查询。取消、关闭会话、断开订阅、删除历史是四种不同操作。

后续按同一接纳和事件规则扩展模型设置、历史分支、压缩、资源重载与扩展命令；扩展命令不因通过 API 调用而隐式触发模型。

不设置“takeover”所有权移交接口：新客户端获取快照并订阅即可操作。会话列表、历史和工作区查询仍须授权，不能因它们是只读接口而默认公开。

# 07 命令幂等、输入回执与错误

## 7.1 提交与接纳

```http
POST /v1/sessions/s_123/runs
Idempotency-Key: cmd_456
Content-Type: application/json

{"kind":"prompt","text":"分析项目并补充测试",
 "expectedLeafId":"entry_789"}
```

```json
{
  "commandId": "cmd_456",
  "sessionId": "s_123",
  "runId": "r_001",
  "status": "accepted"
}
```

accepted 表示应用服务已登记命令并预留运行，不表示模型已消费输入、历史已持久化或任务成功。返回前应建立稳定 commandId / runId 关联；后续启动失败也应可查询，而不是遗失任务身份。

补充输入的接纳回执另含 inputId 和 targetRunId；只有内核权威输入管理组件已登记该输入，才可返回接纳成功。应用层仅预留 commandId 不足以证明输入已接纳；响应丢失时按同一命令身份核对，不能生成第二条输入。

## 7.2 幂等和冲突

去重范围为已认证主体、Session、操作类型及幂等键。相同键和相同规范化请求返回原接纳结果；相同键但请求不同返回冲突。并发重复请求也必须只创建一个 Run，不能采用无保护的“先查询后插入”。

补充输入的请求身份包含目标 runId、mode 和内容；同一命令重试返回同一 inputId，不能改变目标 Run。已接纳命令的去重查找应先于 RUN_INPUT_CLOSED 校验，保证目标 Run 结束后仍可取得原回执。

查找已有命令应先于重新检查旧请求的 expectedLeafId，避免一次成功请求的合法重试因历史前进而被误判。只有真正的新命令才执行预期版本校验。

内存去重须公布有效期限和容量边界；活跃命令不能提前淘汰。服务实例变化或去重记录过期后，客户端应显示“执行结果待确认”并查询历史，不自动重提有副作用的任务。

## 7.3 补充输入记录与状态

本节规定 steer / follow-up 的首次注入状态。prompt 的接纳由 Run 回执表达。每次补充输入提交具有 commandId，获准接纳后获得稳定 inputId；同一命令的网络重试不创建新输入。

```text
pending -> applied_to_context | not_applied
pending -> reconciliation_required
reconciliation_required -> applied_to_context | not_applied
```

| 状态 | 权威含义 | 客户端可推导的行为 |
|---|---|---|
| pending | 已接纳，尚未确认进入产品正式历史 / 上下文 | 仅在目标 Run 仍有效时具有首次注入资格；不重复提交 |
| applied_to_context | 已按内核契约接纳为正式历史 / 上下文，存在 entryId | 可以定位历史；不表示请求已到达 Provider 或模型遵循了要求 |
| not_applied | 本次投递已终结，且确认没有进入正式历史 / 上下文 | 保留记录与原因；用户可显式创建新输入 |
| reconciliation_required | 基础设施故障导致应用结果无法确认，投递资格已冻结 | 等待权威记录核对；不据此断言未应用或自动重试 |

内部可以存在 claimed、applying 等短暂状态，但出队不等于应用成功。applied_to_context 的边界是产品认可的历史提交，文件模式沿用“写入文件 → 接纳内存树”的现有顺序；它不扩大存储 durability 承诺，也不保证随后的模型请求包含或执行该要求。

InputRecord 的建议最小字段如下，具体 JSON 类型在详细协议中固定：

| 字段 | 语义 |
|---|---|
| inputId / commandId | 输入身份及最初提交命令的关联 |
| sessionId / targetRunId | 记录归属及唯一首次注入范围 |
| mode / content | 不可变的 steer 或 follow-up 请求内容 |
| state | 当前应用状态 |
| entryId | applied_to_context 时必须存在的正式历史关联 |
| terminalReason | not_applied 时的终结原因，例如目标 Run 已结束或取消 |
| sourceInputId | 用户显式再次提交时，可选关联原输入；不复活原记录 |

基础设施故障时，不能仅因队列已空或事件没有送达就标记 not_applied。优先从权威输入记录及可靠 inputId / entryId 关联核对；缺少证据时保持 reconciliation_required，并终止自动投递。服务重启导致内存记录丢失时，适用 §11 的未知结果语义，不能凭历史文本重建关联。

## 7.4 输入生命周期与显式再次提交

| 事件 | 输入处理规则 |
|---|---|
| 客户端退出或断线 | 不改变输入状态，目标 Run 继续按规则处理 |
| 内部压缩、溢出恢复 | 保持同一产品 Run 范围，不因底层尝试结束而终结输入 |
| Run 正常、失败或取消结束 | 结算剩余输入：确认未应用则为 not_applied，无法确认则显式待核对；不迁移执行资格 |
| 取消请求接纳或决定最终结束 | 关闭新输入接纳，已接纳输入按实际提交结果结算 |
| 切换分支或 resetLeaf | 旧 Run 尚未应用的输入不注入新分支；已经进入历史的输入按分支历史处理 |
| 用户以补充输入再次提交未应用要求 | 创建新的 commandId / inputId 并指定新的目标 Run，可关联 sourceInputId；原记录保持终态 |

再次提交属于新的显式操作，不因客户端重连、回执丢失或看到 not_applied 自动触发。若当前没有可接纳补充输入的 Run，用户可显式以 prompt 创建新 Run，不能把补充输入挂到一个尚不存在的目标上。应用结果待核对时不提供自动再次提交，已应用输入也不作为未应用输入重投。

## 7.5 错误分类

| 类别 | 典型错误码 | 客户端行为 |
|---|---|---|
| 业务冲突 | SESSION_BUSY / STATE_CONFLICT | 刷新状态，保留用户输入；不改写为其他操作 |
| 输入接纳关闭 | RUN_INPUT_CLOSED | 查询目标 Run 和原输入回执；不自动改投下一 Run |
| 幂等冲突 | IDEMPOTENCY_CONFLICT | 提示键与内容不一致，不重复执行 |
| 恢复失败 | CURSOR_EXPIRED / EPOCH_CHANGED | 重新取快照，不重提任务 |
| 鉴权 / 校验 | UNAUTHORIZED / FORBIDDEN / INVALID_ARGUMENT | 修正凭证、权限或输入 |
| 服务异常 | INTERNAL_ERROR / SERVICE_UNAVAILABLE | 通过 requestId 查询诊断，不据此断言任务未执行 |

错误信封包含 code、message、requestId 和必要的脱敏 details；HTTP 状态码及各操作的可重试规则在详细协议中确定，不直接向客户端返回异常栈。

# 08 事件协议与稳定标识

## 8.1 统一事件信封

```json
{
  "schemaVersion": 1,
  "sessionId": "s_123",
  "runId": "r_001",
  "streamEpoch": "e_7",
  "seq": 128,
  "type": "message.delta",
  "data": {
    "messageId": "msg_003",
    "partId": "part_0",
    "text": "正在检查测试配置"
  }
}
```

seq 在同一 Session 的 streamEpoch 内严格递增；epoch 在流重建时变化，不仅限于进程重启。它们共同构成游标。SSE id 可编码该游标，JSON 信封保持同一身份，避免传输层与业务层各自排序。

## 8.2 建议事件类别

| 事件类别 | 示例 | 语义 |
|---|---|---|
| 运行 | run.accepted / run.started / run.finished | finished 带 outcome，不等于始终成功 |
| 消息 | message.started / delta / completed | 稳定消息和内容块 ID；完成后关联 entryId |
| 工具 | tool.preparing / update / completed | preparing 不宣称工具已执行 |
| 审批 | approval.requested / resolved / expired | 状态变更可被所有授权客户端观察 |
| 输入 | input.accepted / applied_to_context / not_applied / reconciliation_required | 携带 inputId 与 targetRunId；应用确认包含 entryId，待核对不表示未应用 |
| 会话与维护 | session.changed / operation.finished | 不依赖某个客户端本地推测 |
| 诊断 | diagnostic | 脱敏的可恢复诊断，不替代 Run 终态 |

## 8.3 消息与工具映射约束

消息使用结构化内容块，区分文字、工具调用、工具结果和扩展消息，不把一切拼成 Markdown。未知可选内容可降级展示；遇到不能安全解释的关键状态变化应重新同步或报告协议不兼容。

现有 ToolStarted 表示进入 prepare，仍可能校验或审批失败；不能直接翻译为“命令已执行”。并行工具更新也不天然拥有跨工具的总顺序，应用层应按接纳顺序分配 seq，同时保留各工具关联。[R5]

工具更新显式区分 delta 与 snapshot；快照替换，增量追加。大量输出使用有界尾部或产物引用，并标注 truncated。不得静默丢弃正文增量后仍宣称客户端已完整同步。

# 09 快照、重连与多端接管

## 9.1 标准接管流程

**步骤 1：识别服务与会话。**新客户端完成认证和能力握手，选择原 sessionId，不新建或重新打开一个平行会话。

**步骤 2：取得一致性快照。**返回 SessionView 和 cursor S。视图包含生命周期、活动 Run、输入接纳是否开放、当前历史位置、流式消息、工具状态、审批及必要配置。输入视图包含 targetRunId、应用状态、entryId 或未应用原因，并保留已结束 Run 的未应用和待核对记录；记录较多时使用与快照一致的分页引用。

**步骤 3：补齐历史展示。**历史较大时，以快照指定的 historyRevision 和分支读取分页，避免混入同时发生的新分支变化。

**步骤 4：订阅 S 之后的事件。**服务器重放保留事件并无缝切换到实时推送；客户端按 epoch + seq 去重，使用相同 reducer 更新视图。

**步骤 5：恢复操作。**审批、补充输入和取消都针对快照中的明确对象。若版本已变，服务器返回冲突，客户端重新确认而非猜测目标。

## 9.2 一致性要求

快照与游标必须来自同一个投影提交边界。事件接纳、投影更新、序号分配和进入重放缓冲应形成可观察的一致顺序，不能分别读取内核状态后随意附加一个最新 seq。

从重放切换为实时订阅也必须消除时间窗口：在同一串行化边界登记订阅和取得重放水位，或采用等价机制。并发发生的事件可以重复送达，但不能遗漏；客户端承担去重。

游标过期、epoch 不同或出现不可恢复缺口时，返回明确的重新同步要求。订阅已建立后发现缺口，可发送控制通知后断开，由客户端重新取快照；不能默默跳到最新位置。

## 9.3 背压与断线隔离

内核 emit 只等待服务端事件桥完成接纳，不等待所有客户端接收。现有 CodingAgentEventSink 的返回 stage 会被运行等待，因此必须将网络推送从该等待链路中隔离。[R4]

每个订阅使用有界缓冲。慢订阅者达到上限后断开并重同步，不拖住 Agent；浏览器写入失败只销毁该订阅。事件桥自身的映射、存储或投影失败属于服务基础设施故障，不能与订阅失败一起吞掉。

## 9.4 客户端状态更新规则

同一版本客户端应使用一致的 reducer：相同快照和事件得到相同业务视图。message.completed 可用权威完整内容替换流式片段；工具 snapshot 不再次追加；run.finished 后仍允许查询历史和最终结果。

输入状态按 inputId 更新，applied_to_context 关联 entryId。run.finished 可见时，该 Run 的已接纳输入不能仍具有 pending 投递资格；输入结果以显式事件或一致性快照提供。客户端不能从 Run 的 outcome 推断每条输入是否应用，也不能在切换分支或启动下一 Run 时恢复旧输入资格。

断线期间未确认的提交保持“结果待确认”。重新连接不自动触发 prompt；只有确认原命令未接纳或用户显式重新提交时才创建新任务。

# 10 工具审批与多端操作

## 10.1 审批作为正式服务能力

现有 CodingToolPolicy.evaluate 返回 CompletionStage<Decision>，可作为异步审批桥接点；Policy 文档也明确授权不等于文件或进程沙箱。[R6]

```text
工具请求 -> 固定审批请求快照 -> PendingApproval
        -> 发布 approval.requested
        -> 任一授权客户端提交决定
        -> 原子结算 Policy future -> 工具继续或拒绝
```

审批对象绑定 sessionId、runId、toolCallId 和具体请求版本。允许决定只对该请求有效，不能修改参数后继续复用原批准。展示内容需足以让用户理解副作用，同时屏蔽敏感凭证。

## 10.2 状态与竞争处理

建议状态为 pending、allowed、denied、expired、cancelled。只允许 pending 原子迁移到一个终态。先确定终态和发布一致的状态，再在锁外完成等待 future，避免同步回调造成死锁或重复执行。

| 情况 | 处理规则 |
|---|---|
| 原 TUI 退出 | 保留审批，不自动同意，也不因连接断开立即拒绝 |
| 新客户端接管 | 从快照恢复所有仍有效的待审批事项 |
| 两端同时决定 | 首个合法决定生效；另一个返回已有结果 / 冲突 |
| 相同决定重试 | 返回已提交结果，不再次执行工具 |
| Run 取消或真正关闭会话 | 取消相关审批并结算等待；后到决定不生效 |
| 审批超时 | 按明确策略拒绝 / 终止等待，不自动批准 |

首期只支持“允许本次”和“拒绝本次”。长时等待上限及其与工具超时、取消信号的优先关系需要细化，但不能由某个客户端是否在线决定。

## 10.3 多端协作规则

首期允许多个已授权客户端同时查看与操作，不引入独占控制权和 /takeover 接口。新 prompt 竞争由单运行接纳解决；分支与设置修改由预期版本解决；取消通过 runId 防止误伤新任务。

clientId 仅用于来源标识和审计展示，例如“由 Desktop 审批”，不代表权限。后续如需只读观察者或多人协作，应显式增加角色和权限；如需独占控制，再设计租约、过期、抢占与 fencing，不能仅靠前端隐藏按钮。

# 11 历史持久化与故障语义

## 11.1 数据分工与首期持久化范围

| 数据 | 首期建议 | 边界 |
|---|---|---|
| 正式会话历史 | 复用内核 JSONL 文件模式 | 服务持有 writer；不复制第二份聊天事实 |
| 模型、资源和授信配置 | 复用现有显式配置机制 | 凭证不进入对外视图或事件日志 |
| 活跃 Run、审批 | 服务内存托管 | 不承诺跨进程恢复等待 future |
| 输入记录及回执 | 内核权威管理，应用层维护查询投影；首期保存在服务内存 | Run 结束不删除未应用结果；不承诺关闭 Session 或服务重启后保留这些记录 |
| SessionProjection | 内存中持续维护 | 无客户端也更新；历史可用于后续重建 |
| 事件重放缓冲 | 按数量 / 字节 / 时间有界 | 不是永久日志；过期后使用快照 |
| 幂等记录 | 明确保留期限的内存表 | 不承诺跨服务重启去重 |

服务托管的正常会话建议默认使用文件历史模式；临时内存会话应显式标识其丢失边界。正式历史只记录内核认可的历史条目，不把每个 token 写进同一历史树。

已应用输入的正文可作为正式历史保存；这不等于完整 InputRecord、inputId / entryId 关联或未应用输入已经持久化。记录的保留期限、容量与过期查询结果必须公开；不能淘汰仍有投递资格的记录来规避结算。已终结记录过期时明确返回不可用，不重新赋予执行资格。

## 11.2 故障承诺分层

**客户端断开：**服务存活时，Run、审批和投影继续；重连即可恢复。

**服务异常退出：**仅恢复已成功保存且通过内核校验的历史。内存中的消息片段、审批和回执可能丢失；不自动推断最后一个工具未执行。

**主机重启或断电：**不能超出实际存储 durability 承诺。仓库 README 说明普通 JSONL append 不逐条 force，不保证断电持久性。[R1]

## 11.3 安全恢复策略

新进程使用新 instanceId 和流 epoch。客户端发现实例变化后重新认证、获取历史和状态，对未确认命令提示检查结果；不自动重新提交。

只有存在可靠的持久化运行记录时，才能把对应在途 Run 标记为 interrupted。没有记录时应说明“上次运行结果未知”，不能凭空重建一个确定的失败结论。未来可增加小型操作登记存储，但不能据此宣称工具执行恰好一次。

取消、切换历史分支和重新打开会话都不等于文件回滚。要恢复文件状态，需独立的版本控制或工作区快照机制；不能把历史树当成工作区事务日志。

## 11.4 资源限制

对活跃 Session / Run、审批数、事件缓冲字节数、消息片段和工具输出设定显式限制。接近限制时返回受控错误或要求重同步，不使用无限队列隐藏压力。具体默认值及配置入口列入详细设计。

# 12 安全、工作区与部署边界

## 12.1 默认安全边界

首期本地服务仅监听 loopback，启用认证并限制允许来源；远程接入通过显式配置的 TLS 入口或安全隧道，不默认公开监听端口。CORS 只控制浏览器来源，不能替代身份认证和操作授权。

对会话、历史、工具、工作区、审批和服务管理分别校验权限。任何网页都不应仅因为运行在同一台机器就能指挥 Jcode 执行命令。

| 边界 | 设计要求 |
|---|---|
| 本地服务发现 | 运行目录和凭证文件限制权限；握手验证实例身份 |
| 浏览器接入 | 优先同源；Cookie 方案配套 CSRF 防护，或使用受控的令牌式流请求 |
| 凭证传输 | 不把长期 Token 放在 URL、日志或可分享的会话链接中 |
| 模型凭证 | 只在服务端解析和使用；不下发到三端 |
| 输出与日志 | 文本、工具参数、路径、异常和 Provider 数据分级脱敏 |
| 审批提交 | 验证目标事项及请求快照，防止越权与过期决策重放 |

## 12.2 工作区归属与授权

workspaceId 映射到服务端授权目录。创建或选择工作区应经过本地可信操作或有权限的 API，不能直接把浏览器提交的任意绝对路径交给文件工具。

路径规范化、越界与符号链接处理需明确策略。即使做了路径校验，开放 shell 后也不能宣称建立了真正隔离；需要强隔离时由操作系统账户、容器或独立执行环境实现。

## 12.3 多 Session 与同一工作区

同一 Session 单 active Run 不等于不同 Session 之间不会同时修改文件。首期建议对同一受管 workspace 的具备写入 / shell 能力的活跃 Run 实施保守互斥；已知只读运行可按策略并行。

互斥只约束经过本服务调度的工作，不保护外部编辑器、其他服务实例或未纳入调度的后台进程。后续可引入每任务独立 worktree / 容器，但它们不属于 API 本身提供的保证。

## 12.4 运行与运维

支持客户端自动发现服务和运维显式运行服务两种方式；是否采用 systemd、launchd 或 Windows 服务属于平台实现选择。服务正常退出要排空接纳、结算在途工作并释放 writer；强杀、登出和断电的语义必须与“客户端退出”区分。

# 13 内核接缝、客户端 SDK 与可观测性

## 13.1 开发前需核验或补充的接缝

| 接缝 | 现有基础 / 风险 | 拟采用的约束 |
|---|---|---|
| 运行接纳与身份 | Session 返回观察 stage；API 还需要 commandId / runId | 先建立关联与应用占用；不以 stage 存在推断输入已持久化 |
| 运行终态 | 内部完成事件与公开 stage 可能不在同一结算点 | 核验时序，由单一协调器对外提交一次终态 |
| 消息与历史关联 | 流式对象与历史 entry 是不同层次 | 增加可靠 ID / 提交通知；不按文本匹配 |
| 输入身份与范围 | 当前 PendingMessageQueue 无 inputId / 产品 Run 范围 | 内核接纳稳定 inputId 与范围标识，范围跨越内部压缩和恢复 |
| 接纳、应用与范围关闭 | 检查 running 或简单出队不能判定竞态结果 | 权威组件线性化接纳及关闭；保留 claimed / applying 的身份并结算 |
| 输入应用确认 | 出队、正式历史接纳、请求模型是不同边界 | 以 inputId / entryId 确认 applied_to_context；故障时核对权威记录 |
| 输入终结 | 现有队列可能跨 Run 留存 | 产品最终结束前关闭接纳并结算全部输入；未应用输入不迁移到下一 Run |
| 忙碌与维护状态 | running 无法表达全部维护接纳条件 | 应用占用与内核最终校验协同，不读取多个无关状态拼接 |

现有 prompt 文档明确：取消返回的观察 stage 不取消已接纳运行，可复用这一执行与观察分离原则。[R2]

产品 Run 范围标识可以来自宿主，但内核使用的值类型不能依赖 HTTP DTO 或应用层模块。应用层负责鉴权、幂等和视图组织，内核负责真实投递资格及历史接纳；不通过第二套应用层输入队列模拟严格模式。

## 13.2 终态与释放顺序

应用服务应将内核最终结果、异常和取消统一归一化。内部完成事件只供接纳与映射，不与返回 stage 各自发布一遍 run.finished；也不能让内部 EventSink 等待它自身阻塞着的最终 stage。

产品运行确定最终结束时，先由内核关闭输入接纳，等待正在进行的输入提交结算，并为剩余输入建立应用、未应用或待核对结果；这一边界必须早于最终完成事件的 sink 背压等待。内部压缩和恢复仍可继续的中间尝试不触发该步骤。

内核真正结算后，应用服务核对权威输入记录，按同一会话串行边界提交输入结果投影、更新 Run 结果、释放应用占用并提交 run.finished，再允许后续命令通过接纳。事件桥故障不能抹去已经形成的 inputId / entryId 关联。保证客户端看到旧 Run 已结束后，不会仅因旧占用未释放而误报忙碌；若另一客户端已抢先启动新 Run，返回忙碌仍是合法结果。

终态归一化同时检查最终 CodingAgentRunResult 的 stop reason 和异常，cancelRequested 单独保留。模型 ERROR 即使通过正常完成的 stage 返回也应归为失败；取消请求记录不覆盖实际成功或基础设施失败，不强制把 cancelling 收敛为 cancelled。

“一次终态”是服务端的逻辑提交保证，不是网络恰好一次传输保证。SSE 重放仍可能重复，客户端必须去重；服务崩溃也可能使未持久化终态不可见。

## 13.3 SDK 与协议版本

使用一份协议 schema 生成或校验请求、响应和事件类型。SDK 另行实现鉴权、幂等键保留、游标管理、缺口恢复和 reducer；不能认为生成类型就完成了客户端协议。

capabilities 返回 instanceId、协议版本、支持的操作和限制。HTTP 主版本与事件 schemaVersion 的兼容规则需固定；状态枚举新增不默认视为无风险兼容。三端共享契约测试，避免相同事件产生不同状态。

## 13.4 可观测性

记录 requestId、commandId、sessionId、runId、inputId、entryId、toolCallId、approvalId 的关联；观测活动会话、运行时长、输入应用及未应用结果、审批等待、订阅滞后、重同步、取消耗时与事件桥失败。日志默认不保存完整提示词、工具参数和凭证，审计记录与用户聊天历史分开管理。

## 13.5 Java 嵌入接口的兼容策略

现有跨 Run 队列语义有测试保护，严格模式应作为显式行为变更处理。建议首期保留旧 Java 嵌入接口的兼容模式，统一服务创建 Session 时显式选择严格的产品 Run 级模式；同一 Session 的模式固定，不混用两套投递保证。

兼容模式继续由现有测试验证，严格模式增加独立契约测试，不直接改写旧测试期望。公开配置类型、旧接口最终迁移的版本边界和默认值策略在详细设计中确定；统一服务的严格保证不能因兼容模式存在而降级。

# 14 实施路线与验收标准

## 14.1 分阶段交付

| 阶段 | 主要工作 | 退出条件 |
|---|---|---|
| A：契约、内核接缝与应用层 | 固定身份、状态、错误和事件；实现产品 Run 范围、输入确认及结算，再接入 ManagedSession、投影和内存重放 | 严格输入与兼容模式测试分别通过；无需 UI 即可验证接纳、应用和终结竞态 |
| B：独立服务闭环 | 服务发现、认证、HTTP / SSE、审批、取消、快照及重连 | 两个简单客户端完成退出后接管；故障矩阵通过 |
| C：三端与高级能力 | SDK、TUI / WebUI / Desktop；再接入分支、模型、压缩、资源及扩展命令 | 三端同契约一致；高级操作复用接纳与维护模型 |

先验证服务与协议，不以完整 UI 为前置。无需同时开发多套传输、多人协作和崩溃续跑；框架和默认限制在阶段 A 完成详细选型。

## 14.2 必须通过的验收场景

| 编号 | 场景 | 验收结果 |
|---|---|---|
| T01 | TUI 提交任务后直接退出 / 被终止 | 服务与原 Run 继续；无关联取消 |
| T02 | 无客户端时任务产生审批，随后 WebUI 接入 | 快照恢复待审批；批准后原调用继续 |
| T03 | 任务运行中 Desktop 接管 | 恢复消息、工具、输入回执和当前配置 |
| T04 | 提交响应丢失后按同一幂等键重试 | 同有效期内只产生一个 Run；回执一致 |
| T05 | 两端并发 prompt、审批、取消 | 符合接纳矩阵；不误取消后续 Run |
| T06 | 慢客户端、断线及游标过期 | 不拖住 Agent；无静默事件缺口 |
| T07 | 收到终态后立即提交下一任务 | 旧占用已释放；终态不重复提交 |
| T08 | snapshot 与实时事件高并发交错 | 无事件遗漏；重复可去重；视图一致 |
| T09 | 服务异常退出后重启 | 恢复可用历史；不自动重放未知副作用 |
| T10 | 两客户端同时自动启动服务 | 同配置目录只形成一个合法服务实例 |
| T11 | 产品最终完成事件等待 sink 时提交迟到输入 | 返回 RUN_INPUT_CLOSED；旧命令合法重试仍返回原回执，不在下一 Run 执行 |
| T12 | 取消或模型 ERROR 结束时仍有待处理输入 | 按事实结算为 applied_to_context、not_applied 或待核对；下一 Run 不消费旧待处理输入 |
| T13 | Run 结束后 branch() / resetLeaf() 并发起新 Run | 不注入旧未应用输入；已进入历史的输入按分支正常继承 |
| T14 | 输入出队后、正式历史提交前发生取消 | 出队不冒充已应用；保留 inputId 并按真实提交结果结算，应用时关联 entryId |
| T15 | 上下文溢出触发压缩与内部 continueAfterFailure() | 保持同一产品 Run 范围；输入不因中间尝试结束而提前终结 |
| T16 | 输入接纳与范围关闭并发 | 要么稳定接纳且最终可查，要么明确拒绝；无丢失身份、重复注入或跨 Run 迁移 |
| T17 | 已正常完成执行、最终交付阶段接纳取消 | 允许 completed 且 cancelRequested = true；Run 终态只提交一次 |
| T18 | 输入历史已接纳后事件桥失败 | 通过权威 inputId / entryId 关联恢复应用状态；无法确认时显式待核对，不误报未应用或自动重试 |
| T19 | 用户显式再次提交未应用输入，与断线重试并发 | 新意图有新身份并关联来源；原命令重试仍返回旧记录，不复活终结输入 |
| T20 | 旧 Java 接口与统一服务分别运行队列场景 | 兼容模式保留原跨 Run 行为；统一服务显式严格模式，同一 Session 不混用 |

## 14.3 核心端到端演练

客户端 A 创建会话并运行任务 → 强制结束 A → 后台继续并进入审批 → 客户端 B 认证并恢复快照 → B 批准并发送补充输入 → 原 Run 完成 → B 查询结果与历史。

该演练应同时检查无重复执行、inputId / entryId 正确关联、审批只结算一次、原 Run 的未应用输入可查询且不进入下一 Run，以及服务资源释放。本文仅定义测试目标，不表示现有实现已经通过这些测试。

**客户端安全：**浏览器认证模式、远程连接配置、配对与凭证轮换，以及未来只读观察者的权限模型。

## 15.3 后续演进，不作为首期依赖

持久化操作登记与中断诊断；完整输入记录及关联的跨进程持久化；跨进程幂等；显式跨 Run 任务积压；独立 worktree / 容器；交互式终端；多人角色与控制租约；更多传输适配。新增能力不得改变“客户端退出不取消任务”的核心语义，也不得通过残留输入队列隐式引入跨 Run 执行资格。

## 15.4 评审结论模板

AD-09 与 AD-10 已在本轮确定；评审仍需逐项确认 AD-02 至 AD-08 及 AD-11，指定详细设计负责人并关闭必要的未决项。总体评审确认后升级为 v0.2；协议首次实现并通过契约测试后，再建立可追踪的发布版本。本文不预填整体评审通过、责任人或实际完成日期。

## A.2 术语约定

**接纳（admission）：**服务登记并占用执行资格，不等于成功完成或落盘。

**产品 Run：**一次 prompt / continue 对应的完整产品执行范围，包含内部压缩和恢复；用户显式发起的下一次操作属于新的 Run。

**输入应用（applied_to_context）：**输入已被产品接纳到正式历史 / 上下文并关联 entryId；不保证模型收到或遵循该输入。

**未应用（not_applied）：**本次投递已终结，且确认没有进入正式历史 / 上下文；不是模型未遵循要求的同义词。

**待核对（reconciliation_required）：**应用结果缺少可靠证据，首次投递资格已冻结；不能视作未应用或据此自动重试。

**投影（projection）：**由已接纳事件与应用操作组织的客户端业务视图。

**事件流代次（epoch）：**一条会话事件序列的身份边界，用于检测重建与过期游标。

**接管（attach）：**新客户端连接原服务，恢复同一会话的观察和操作能力。

**副作用：**文件写入、进程执行等外部变化；聊天历史重放不能自动撤销或证明其状态。
